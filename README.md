# PKI Lab — Build a Certificate Authority from Scratch

A hands-on lab for understanding Public Key Infrastructure by building a three-tier CA hierarchy (Root CA → Intermediate CA → Leaf Certificate) using OpenSSL.

By the end, you'll have a working internal PKI, a signed TLS certificate, and a real understanding of how certificate chains, trust stores, and X.509 extensions work.

## Prerequisites

- OpenSSL 3.x (check with `openssl version`)
- A Unix-like shell (Linux, macOS, WSL)
- Basic familiarity with the command line

## Step-by-Step Walkthrough

### 1. Directory Setup (`01-setup.sh`)

Creates the working directories and initializes OpenSSL's bookkeeping files.

```bash
mkdir -p root/newcerts intermediate/newcerts certs

# index.txt — OpenSSL's flat-file database of issued certs
touch root/index.txt intermediate/index.txt

# serial — the next certificate serial number (hex)
echo 1000 > root/serial
echo 2000 > intermediate/serial
```

**Why:** OpenSSL's `ca` command is stateful. `index.txt` tracks every cert ever issued (status, expiry, serial, subject). `serial` provides the next serial number — X.509 requires each cert from a CA to have a unique serial. `newcerts/` stores a copy of every signed cert, named by serial, as an audit trail.

---

### 2. Root CA (`02-root-ca.sh`)

Generates the root CA's private key and self-signed certificate.

```bash
# Generate a 4096-bit RSA key, encrypted at rest with AES-256
openssl genrsa -aes256 -out root/root.key 4096

# Create a self-signed certificate valid for 10 years
openssl req -config configs/root.cnf \
  -key root/root.key \
  -new -x509 -days 3650 \
  -extensions v3_ca \
  -out root/root.crt

# Inspect the result
openssl x509 -in root/root.crt -text -noout
```

**What each flag does:**

| Flag | Purpose |
|------|---------|
| `genrsa -aes256` | Generate RSA key; `-aes256` encrypts the key file with a passphrase so it's protected at rest |
| `req -new -x509` | `-new` creates a new certificate request; `-x509` self-signs it immediately instead of producing a CSR |
| `-config configs/root.cnf` | Read subject fields, defaults, and extensions from this config file |
| `-key root/root.key` | Use this private key (OpenSSL will prompt for the passphrase) |
| `-days 3650` | Certificate validity period (~10 years); root CAs have long lifetimes |
| `-extensions v3_ca` | Apply the `[ v3_ca ]` extensions section from the config (adds `CA:TRUE`, `keyCertSign`) |
| `x509 -text -noout` | Decode and print the certificate fields; `-noout` suppresses the raw PEM block |

**What to check in the output:**
- `Issuer` and `Subject` are identical (self-signed)
- `CA:TRUE` appears in Basic Constraints
- Key Usage shows `Certificate Sign, CRL Sign`

---

### 3. Intermediate CA (`03-intermediate-ca.sh`)

Generates the intermediate CA's key, creates a CSR, and has the root CA sign it.

```bash
# Generate the intermediate's own key pair
openssl genrsa -aes256 -out intermediate/intermediate.key 4096

# Generate a Certificate Signing Request (not a cert — no -x509 flag)
openssl req -config configs/intermediate.cnf \
  -key intermediate/intermediate.key \
  -new \
  -out intermediate/intermediate.csr

# The root CA signs the CSR, producing the intermediate's certificate
openssl ca -config configs/root.cnf \
  -extensions v3_intermediate_ca \
  -extfile configs/intermediate.cnf \
  -days 1825 \
  -notext \
  -in intermediate/intermediate.csr \
  -out intermediate/intermediate.crt

# Verify: does the intermediate chain back to the root?
openssl verify -CAfile root/root.crt intermediate/intermediate.crt
```

**Key difference from the root:** No `-x509` flag on `openssl req`, so we get a CSR instead of a self-signed cert. A CSR is a request — it contains the public key and subject, signed by the requester's private key (proof of possession), but it's not a certificate yet. The root CA then signs it with `openssl ca`.

**`openssl ca` flags explained:**

| Flag | Purpose |
|------|---------|
| `-config configs/root.cnf` | Use the **root's** config — the root is the signer, so it needs the root's key, cert, database, and serial |
| `-extensions v3_intermediate_ca` | Which extensions section to stamp onto the resulting cert |
| `-extfile configs/intermediate.cnf` | Look for that extensions section in this separate file (it's in the intermediate's config, not the root's) |
| `-days 1825` | 5-year validity; shorter than the root so it can be rotated without updating every trust store |
| `-notext` | Don't embed human-readable text in the PEM output |

**What to check:**
- `CA:TRUE, pathlen:0` in Basic Constraints — can issue leaf certs but not further CAs
- `Issuer` is the root CA, `Subject` is the intermediate CA
- `openssl verify` prints `OK`

### 4. Leaf Certificate (`04-leaf-cert.sh`)

Issues an end-entity (server) certificate for `test.pkilab.local`.

```bash
# Server key — no -aes256 (servers need unattended startup)
openssl genrsa -out certs/test.pkilab.local.key 2048

# CSR with subject passed inline via -subj
openssl req -new \
  -key certs/test.pkilab.local.key \
  -subj "/C=CH/O=PKI Lab/CN=test.pkilab.local" \
  -out certs/test.pkilab.local.csr

# Intermediate CA signs it with leaf extensions
openssl ca -config configs/intermediate.cnf \
  -extensions server_cert \
  -notext \
  -in certs/test.pkilab.local.csr \
  -out certs/test.pkilab.local.crt

# Build the chain file (leaf + intermediate, NOT root)
cat certs/test.pkilab.local.crt intermediate/intermediate.crt \
  > certs/test.pkilab.local.chain.pem
```

**Why 2048-bit for the leaf?** The leaf key only needs to be secure for the certificate's validity period (typically months to a year). A CA key protects everything it ever signs, so it needs more margin. 2048-bit RSA is still considered secure and is faster for TLS handshakes.

**Why no passphrase?** A web server (nginx, Apache, caddy) reads the key on startup without human intervention. An encrypted key would require someone to type a passphrase every time the server restarts. In production, you'd protect the key with file permissions (`chmod 600`) or store it in an HSM.

**The chain file:** In TLS, the server sends its own certificate plus any intermediates so the client can build the chain to a trusted root. The root is NOT included — the client already has it in its trust store. Order matters: leaf first, then intermediates.

**What to check in the leaf cert:**
- `CA:FALSE` in Basic Constraints
- Key Usage: `Digital Signature, Key Encipherment`
- Extended Key Usage: `TLS Web Server Authentication`
- Subject Alternative Names: `DNS:test.pkilab.local`, `DNS:*.pkilab.local`

### 5. Chain Verification (`05-verify.sh`)

Validates the full chain offline.

```bash
# Full chain verification
openssl verify -CAfile root/root.crt \
  -untrusted intermediate/intermediate.crt \
  certs/test.pkilab.local.crt
```

**`-CAfile` vs `-untrusted`:**

| Flag | Role | Analogy |
|------|------|---------|
| `-CAfile` | **Trust store** — certificates here are trusted anchors | Your browser's built-in root CA list |
| `-untrusted` | **Chain-building hints** — used to connect leaf to root, but NOT trusted as roots themselves | The intermediate certs a server sends during TLS |

If you put the intermediate in `-CAfile`, you'd be saying "I trust this intermediate unconditionally" — verification would pass even if the intermediate's own signature from the root was invalid. That defeats the purpose of the hierarchy.

**What OpenSSL checks during verification:**
1. **Signature chain** — each cert's signature is valid under its issuer's public key
2. **Validity period** — no cert in the chain is expired or not-yet-valid
3. **Basic Constraints** — issuers have `CA:TRUE`
4. **Path length** — `pathlen` constraints are respected
5. **Key Usage** — issuers have `keyCertSign`

### 6. Live TLS Test (`06-tls-test.sh`)

Tests the certificate in an actual TLS handshake.

**Terminal 1 — Start the TLS server:**

```bash
openssl s_server -accept 4433 \
  -cert certs/test.pkilab.local.crt \
  -key certs/test.pkilab.local.key \
  -CAfile intermediate/intermediate.crt
```

| Flag | Purpose |
|------|---------|
| `-accept 4433` | Listen on port 4433 |
| `-cert` | The leaf certificate to present to clients |
| `-key` | The private key for the TLS handshake (server proves possession during CertificateVerify) |
| `-CAfile` | Intermediate cert(s) to send alongside the leaf in the TLS Certificate message |

**Terminal 2 — Connect as a client:**

```bash
openssl s_client -connect localhost:4433 \
  -CAfile root/root.crt
```

| Flag | Purpose |
|------|---------|
| `-connect localhost:4433` | Where to connect |
| `-CAfile root/root.crt` | The client's trust store — only our custom root is trusted |

**Expected output (client side):**

```
depth=2 C = CH, O = PKI Lab, CN = PKI Lab Root CA
verify return:1
depth=1 C = CH, O = PKI Lab, CN = PKI Lab Intermediate CA
verify return:1
depth=0 C = CH, O = PKI Lab, CN = test.pkilab.local
verify return:1
---
Verify return code: 0 (ok)
```

`verify return:1` at each depth means that level passed. `Verify return code: 0 (ok)` is the final verdict.

**Test hostname verification:**

```bash
# Should succeed — SAN matches
openssl s_client -connect localhost:4433 \
  -CAfile root/root.crt \
  -verify_hostname test.pkilab.local

# Should fail — hostname not in SANs
openssl s_client -connect localhost:4433 \
  -CAfile root/root.crt \
  -verify_hostname evil.example.com
# → Verify return code: 62 (hostname mismatch)
```

**Test without trust anchor:**

```bash
# Uses system trust store, which doesn't have our root
openssl s_client -connect localhost:4433
# → Verify return code: 19 (self-signed certificate in certificate chain)
```

### 7. Break-It Exercises (`07-break-it.sh`)

These are meant to be run manually and explored. The script provides the commands with explanations.

**Exercise A — Issue a leaf without `CA:FALSE` and use it to sign another cert:**

```bash
# Issue a cert without proper constraints
openssl req -new -x509 \
  -key certs/test.pkilab.local.key \
  -subj "/CN=Unrestricted Leaf" \
  -days 365 \
  -out certs/unrestricted.crt

# Try using it to sign something else
openssl genrsa -out certs/rogue.key 2048
openssl req -new -key certs/rogue.key -subj "/CN=Rogue" -out certs/rogue.csr
openssl x509 -req -in certs/rogue.csr \
  -CA certs/unrestricted.crt \
  -CAkey certs/test.pkilab.local.key \
  -CAcreateserial \
  -out certs/rogue.crt

# This "works" — the signature is valid. But a proper verifier
# will reject it because the signing cert lacks CA:TRUE.
openssl verify -CAfile certs/unrestricted.crt certs/rogue.crt
```

**Lesson:** Without extensions enforcement, any certificate can sign any other certificate. Extensions are the policy layer on top of the math.

**Exercise B — Expired certificate:**

```bash
# Issue a cert that's already expired (valid for 0 days, backdated)
openssl ca -config configs/intermediate.cnf \
  -extensions server_cert \
  -startdate 20200101000000Z \
  -enddate 20200102000000Z \
  -notext \
  -in certs/test.pkilab.local.csr \
  -out certs/expired.crt
```

**Exercise C — Wrong SAN:**

```bash

# and try to use it for the original hostname.
```

**Exercise D — Revocation:**

```bash
# Revoke the leaf cert
openssl ca -config configs/intermediate.cnf \
  -revoke certs/test.pkilab.local.crt

# Generate a CRL (Certificate Revocation List)
openssl ca -config configs/intermediate.cnf \
  -gencrl -out intermediate/intermediate.crl.pem

# Verify with CRL checking
openssl verify -CAfile root/root.crt \
  -untrusted intermediate/intermediate.crt \
  -crl_check -CRLfile intermediate/intermediate.crl.pem \
  certs/test.pkilab.local.crt
# → certificate revoked
```
